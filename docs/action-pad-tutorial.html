01 · Start here

The mental model

The Action Pad is a small menu interpreter. config.ts declares a tree of menus and actions. ActionPad.tsx keeps a stack pointing at the current branch, turns each action into a button, and emits callbacks. TabletClient.tsx converts those callbacks into ordered Neovim input.

It is “dynamic” because the same component renders whichever menu is at the top of its stack. Opening a submenu replaces the visible actions, adds a generated Back control, and displays the current path. The configuration describes behavior; it does not contain any React Native layout code.

Three layers, three jobs

1. Configuration

A typed, trusted TypeScript tree: menus, labels, group placement, input sequences, and post-input policy.

2. Presentation

Menu-stack navigation, breadcrumbs, Back insertion, long-press suppression, responsive grouping, and disabled states.

3. Integration

One-shot Ctrl, native-key conversion, IME composition ordering, connection resets, and final controller dispatch.

02 · Source map

Know which file owns what

action-pad/config.ts

Defines the bundled menu tree and validates it at module load. This is the usual file to edit when adding or reorganizing actions.

action-pad/types.ts

Defines ActionMenu, the six-button union, and constants such as the group, input-length, and hold limits.

action-pad/ActionPad.tsx

Renders and navigates the tree. It owns the menu stack and maps action types to callbacks, but does not talk to Neovim directly.

action-pad/validation.ts

Rejects malformed trees, bad key names, duplicates, cycles, overflow, and invalid raw-input payloads before the pad is usable.

TabletClient.tsx

Supplies state and callbacks, manages one-shot Ctrl, coordinates with the Android IME, and forwards ordered input to the controller.

input.ts

Defines accepted native special-key names and converts them to Neovim notation such as <Esc> or <C-Left>.

The barrel file action-pad/index.ts exposes the component, default tree, validator, limits, and public types.

03 · Under the hood

What happens after a tap

config.tstyped menu tree
ActionPadstack + button routing
TabletClientCtrl + key conversion
CodeyImesettles composition in order
Neovimcontroller.input(keys)

The root is validated

config.ts calls validateActionMenu(ACTION_PAD_MENU) immediately. The component validates an injected rootMenu again when its object identity changes.

The component selects the current menu

menuStack begins as [validatedRoot]. A menu action pushes its child; Back removes the final element. The breadcrumb is the labels of every stack entry after the root.

The action type chooses a callback

Native keys call onKeyPress; raw sequences call onRawInput; modifiers toggle Ctrl; keyboard actions focus the IME; branches push menus. A dual action taps like a key and holds like a branch.

The menu applies its post-input policy

After a key, input, or dual tap, the current menu's afterInput decides whether the stack returns to Home or stays open. Navigation uses stay; most command menus use root.

TabletClient prepares input

A native key is converted with specialKeyToNvimInput, including one-shot Ctrl when selected. A raw nvimInput string is already in Neovim notation. Both routes clear Ctrl after use.

The IME preserves ordering

sendOrderedActionInput hands the sequence to the native IME. Any active composition is settled first; the resulting ordered batch comes back to JavaScript and is serialized through orderedDispatchTail before controller.input.

Why route through the IME? A pad command must not overtake text still being composed by the software keyboard. The ordered-input path guarantees “finish composition, then run this action” semantics.

05 · The configuration model

Menus, groups, and six action types

config.ts is executable, trusted TypeScript—not JSON and not a remote user preference. Each menu has identity, a display label, a post-input policy, and exactly two named groups.

Minimum useful menuTypeScript
import type { ActionMenu } from "./types";

export const ACTION_PAD_MENU = {
  id: "root",
  label: "Home",
  afterInput: "root",
  groups: {
    leading: [
      { id: "escape", label: "Esc", type: "key", key: "Escape" },
    ],
    trailing: [
      { id: "save", label: "Save", type: "input", nvimInput: ":w<CR>" },
    ],
  },
} as const satisfies ActionMenu;

Menu fields

FieldMeaningPractical rule
idStable developer identifier.Non-empty. Action IDs must be unique across both groups of the same menu.
labelHuman-facing menu name.Used in breadcrumbs; keep it short enough for the header.
afterInputWhere the stack goes after a leaf dispatch.root for one-off commands; stay for repeated operations.
groups.leadingLeft group below the editor; top group in the right rail.At most 6 configured actions.
groups.trailingRight group below the editor; bottom group in the right rail.At most 6 at root, but 5 in nested menus because Back is appended.

Action types

TypeRequired payloadWhat happensTypical use
keykeyCalls onKeyPress; may consume one-shot Ctrl.Esc, Tab, Enter, arrows, F-keys.
inputnvimInputSends the complete trusted sequence in one ordered operation.Mappings, commands, motions.
menumenuPushes a child menu; sends no editor input.Leader, Search, Window.
dualkey + menuTap sends the key; 450ms hold opens the child and suppresses tap.Arrow + repeated navigation menu.
modifiermodifier: "ctrl"Toggles local one-shot Ctrl state; sends nothing by itself.Ctrl + the next native key.
keyboardnoneFocuses the Android IME; sends no Neovim input and does not consume Ctrl.Open software keyboard.
Labels and payloads are different. The label can say Esc, but a native key must use the canonical value Escape. Validation deliberately rejects aliases that would silently do nothing.

06 · Editing config.ts

Configuration recipes

Add a normal Neovim command

Use input when the action is a complete mapping, motion, or command-line sequence. The string is passed straight to Neovim's input API.

Add inside either groupconfig.ts
{
  id: "toggle-list",
  label: "Toggle List",
  type: "input",
  nvimInput: ":set list!<CR>",
}

Add a native special key

Use key for a canonical name from NvimSpecialKeyName: Backspace, Delete, Enter, Escape, Tab, ArrowLeft/Right/Up/Down, Home, End, PageUp/Down, Insert, or F1–F12.

Native key actionconfig.ts
{
  id: "page-down",
  label: "Page Down",
  type: "key",
  key: "PageDown",
}

Add a submenu

Declare the child before the parent that references it. Choose stay if users will tap several items in sequence; otherwise choose root.

Define child, then link itconfig.ts
const GIT_MENU = {
  id: "git",
  label: "Git",
  afterInput: "root",
  groups: {
    leading: [
      { id: "status", label: "Status", type: "input", nvimInput: "<Space>gs" },
      { id: "blame", label: "Blame", type: "input", nvimInput: "<Space>gb" },
    ],
    trailing: [], // Back is generated here at runtime
  },
} as const satisfies ActionMenu;

// Add this branch action to its parent:
{ id: "git", label: "Git", type: "menu", menu: GIT_MENU }

Add a tap/hold dual action

Dual is intentionally specialized: its tap side is a native special key, and its hold side is a submenu.

Tap key, hold menuconfig.ts
{
  id: "down",
  label: "↓",
  accessibilityLabel: "Down; hold for navigation options",
  type: "dual",
  key: "ArrowDown",
  menu: DOWN_NAVIGATION_MENU,
}

Choose the correct afterInput

afterInput: "root"

Best for commands whose next likely action is unrelated: Save, Find File, Rename, Split, Terminal.

afterInput: "stay"

Best for repeated operations: move 5 lines several times, page repeatedly, or step through a sequence.

Raw input is trusted code. Do not load action trees from the network or accept arbitrary user-authored nvimInput sequences. Keep them in the application bundle and review them like source code.

07 · Adaptive rendering

One tree, two placements

Portrait / square: below

The pad sits below the editor. Leading and trailing stay on the left and right. Each group is split into two rows using ceil(items / 2) columns.

Landscape: right

The pad becomes a fixed 336dp right rail. Leading is at the top, trailing at the bottom, actions use two 48%-width columns, and the shared area can scroll vertically.

What does not change during rotation

TabletClient passes placement={landscape ? "right" : "below"} to the same mounted pad. The component changes its layout branch without resetting menuStack, so the current submenu survives rotation.

Compact mode

When the software keyboard reduces measured height by at least 120dp, TabletClient enables compact. Spacing, padding, radii, and type shrink, while buttons keep a 48dp minimum touch size. The landscape rail remains scrollable if the keyboard leaves too little vertical room.

Back is configuration-aware

Back is not declared in config.ts. It is appended to the trailing group whenever the stack has more than one menu. That is why nested trailing groups may configure only five actions: the sixth visual slot is reserved.

08 · Safety rails

What validation guarantees

TypeScript catches many mistakes while authoring, but the runtime validator protects any injected menu object and enforces constraints the type system cannot express conveniently.

  • Every menu and action has a non-empty id and label; optional accessibility labels must also be non-empty.
  • Every menu has exactly leading and trailing arrays and a valid root/stay policy.
  • Each group has at most six configured actions; nested trailing groups have at most five.
  • Action IDs are unique across both groups of the same menu.
  • Native keys use the canonical supported names, including only F1 through F12.
  • Raw input is non-empty and no longer than 16,384 characters.
  • Menu and dual targets are objects, every action type has its required payload, and ancestor cycles are rejected.
Identity scope: duplicate action IDs are forbidden among siblings in one menu, including across leading and trailing. The same ID may be reused in a different menu, which is why the built-in tree can have several context-specific actions named down or files.

Why use both compile-time and runtime checks?

satisfies ActionMenu

Checks the literal without widening its useful values. You get editor completion and immediate TypeScript feedback in config.ts.

validateActionMenu(...)

Checks values at runtime, provides path-specific errors, detects cycles and duplicates, and protects custom roots supplied through component props.

09 · Day-to-day development

A safe way to evolve the pad

Start from the user job

Decide whether this should be a repeatable menu, a one-shot command, a native key, or simply access to another branch. Avoid nesting for one lonely action.

Find the owning menu in config.ts

Keep related commands together. Placement is semantic as well as visual: leading maps to left/top; trailing maps to right/bottom.

Add a small typed literal

Use a stable kebab-case ID, a short label, and an accessibility label when the visual label is symbolic or the gesture needs explanation.

Check capacity and navigation policy

Count both groups, remember the nested trailing Back slot, and set afterInput on the menu that users will be in when the leaf is pressed.

Run focused verification

Type-check the Android app, then run the Action Pad tests. Add a behavior test when introducing a new branch shape or interaction rule.

Reload on the tablet

Ordinary config.ts changes are JavaScript/TypeScript changes, so Metro reload or an app rebuild is enough. A native prebuild is not required unless native configuration or Kotlin changes too.

Focused checks from repository rootshell
pnpm --filter @codey/android typecheck
pnpm --filter @codey/android exec jest --runInBand src/action-pad

10 · Keep these sharp edges in mind

Common mistakes and their fixes

Using Esc as a key

Problem: that is a display label, not a canonical key. Use: key: "Escape".

Expecting Ctrl to rewrite raw input

modifier applies Ctrl to the next native key. An input sequence should contain its own notation, such as <C-r>; raw input clears the one-shot state.

Putting afterInput on a button

The policy belongs to the current menu. All key/input leaves in that menu share it.

Configuring Back manually

Do not. The component creates Back whenever it is below root and guarantees it is the final trailing action.

Six nested trailing actions

Validation rejects this because it would leave no room for Back. Move one action to leading, remove it, or create another branch.

Assuming disconnect preserves navigation

Disabling the pad or changing resetKey returns it to root. The current integration uses connection phase as the reset key.

Breaking Neovim mappings

Entries such as <Space>sg depend on the host's Neovim setup. Update the pad when mappings change, and test the actual target configuration.

Forgetting gesture accessibility

Give symbolic dual actions an explicit label describing both tap and hold. The UI already supplies a dual-action accessibility hint.

The simplest extension rule: keep config.ts declarative, keep Neovim sequences explicit, use menus for organization rather than logic, and move into component or integration code only when the schema truly cannot express the behavior.
